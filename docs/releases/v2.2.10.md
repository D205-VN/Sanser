# Sanser 2.2.10

This release addresses two separate latency mechanisms. It does not promise a
5–15 ms WAN route or claim the user's ~183 ms UDP echo has been eliminated.

## Router paths in both directions

The actual single-socket candidate gatherer now attempts PCP and NAT-PMP before
falling back to UPnP, concurrently with STUN gathering. Previously those two
mapper implementations existed but were not called by the desktop app. The
default IPv4 gateway is read from the OS, rather than guessed from a subnet.
Windows gateway discovery runs without a console window.

PCP uses the source IP selected after connecting its UDP socket to the router;
the former implementation serialized 0.0.0.0. Replies must match the connected
router endpoint, MAP nonce, UDP protocol and internal port. NAT-PMP first queries
the external-address opcode; previously it returned the private gateway address
as the public endpoint. Its MAP reply must match the requested internal port.
Both protocols use bounded retries and validate returned ports/lifetimes. Only
public, compatible mapped candidates enter normal authenticated path selection.

This can provide a public Direct alternative to a slow VPN/overlay **when the
router supports and permits the mapping**. CGNAT, upstream NAT or a router that
refuses all mapping protocols can still require an overlay or relay. The existing
7200-second mapping lifetime is requested; lease renewal/removal and seamless
live route migration are not implemented by this change.

Diagnostics now distinguish the advertised local candidate from the OS-selected
source address/interface of the reserved probe socket and show the mapping
protocol on each endpoint. This is not a media NIC pin or kernel timestamping.
A route already above 80 ms during nomination and live measurement is explicitly
classified as slow at nomination, rather than merely reporting no later rise.

## Mac host → Windows viewer picture latency

The actual VideoToolbox Baseline SPS in prior fixtures advertised POC type 0,
one reference picture and no VUI. Windows decoder tests could retain three final
pictures even with the low-latency API enabled. The Mac encoder now adds an
explicit zero-reorder VUI restriction when there is no existing VUI. It preserves
the reference count, geometry and crop. Frame reordering must be successfully
disabled on the encoder. Existing VUI, unknown profiles and invalid input pass
through unchanged. Encoded dependent P-frames are not arbitrarily discarded.

The Windows regression test feeds **one access unit, then stops input**, and
requires that picture to be decoded and converted before submitting another.
This tests the idle-desktop case where the latest mouse/window change previously
could remain buffered until later activity. Older Mac fixtures remain in the
compatibility tests. Real two-computer end-to-end latency still needs retesting.

References: [Microsoft low-latency codec property](https://learn.microsoft.com/en-us/windows/win32/medfound/codecapi-avlowlatencymode),
[Microsoft hardware video requirements, low-latency H.264 signaling](https://download.microsoft.com/download/A/C/9/AC95E05C-3B35-43F1-86E5-E948A70454E5/Windows%20Hardware%20Compatibilty%20Program_151106.pdf).

Update both desktops. Ordinary Mac → Windows Connect retains its legacy media
pipeline; the Mac-host bitstream change affects Windows → Mac control and Mac
multi-viewer hosting. Group audio remains unimplemented. All 2.2.9 crash and
view-only input fixes remain included.
