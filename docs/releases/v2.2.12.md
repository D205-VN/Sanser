# Sanser 2.2.12

P0 stream stability fixes for the shared SNV2 desktop transport. These apply to
Windows controlling Mac, Mac-to-Mac, Windows-to-Windows and multi-computer
sharing in either direction. Ordinary Mac controlling Windows continues to use
the legacy pipeline. Update both endpoints.

## Denied input must not disconnect a healthy viewer

When the host disabled remote input but the client still sent keyboard/button
events, the old host ignored those reliable packets without acknowledging them.
The client then hit its two-second input delivery deadline and disconnected,
taking the otherwise healthy video window with it. The host now acknowledges
valid ordered delivery without injecting denied events. This does not grant
control permission or relax authentication. Reliable input still fails closed
if the peer genuinely stops acknowledging delivery.

The new loopback regression reproduces the former timeout and requires viewing
to remain active beyond that deadline while the host injects zero denied events.

## Preserve video dependencies across UDP reordering and repair

A later complete P-picture previously erased an earlier incomplete IDR or
reference picture. Repairing the missing fragment could no longer restore it,
which caused black startup or repeated reference/keyframe recovery.
Even a P-picture arriving before the *first* fragment of an IDR could advance
the old receive watermark and reject that late IDR as obsolete.

The reassembler now retains known incomplete dependencies, delivers repaired
pictures in frame-ID order and drains already-complete dependent pictures
immediately. A fresh complete IDR can bypass the broken older chain. Storage is
bounded by 24 pictures, 8 MiB and the existing recovery deadlines. This is not a
fixed playout buffer; complete pictures with no missing known dependency are
delivered immediately once a valid reference exists. The watermark advances
only for a valid reference chain, so an unseen late startup IDR remains usable.
Internal receive IDs do not change the wire format.
An entirely late P-reference also keeps the last valid reference usable during
the recovery window; a dependent P-picture cannot permanently invalidate it
merely by arriving first. Unrecovered whole-picture gaps expire too.

Unit tests cover repaired IDR then buffered P-picture, fresh-IDR bypass, replay
rejection and finite expiry. An encrypted UDP test verifies the same ordering
through Peer and requires the next P-picture to arrive without another IDR.

## Bound startup and live-picture recovery under congestion

Fast paths retain a 3 ms initial gap NACK. Slower paths allow expected picture
serialization and a small 3–20 ms reorder tolerance before declaring a hole or
missing tail, without holding complete pictures. Repeat attempts use the existing input
ACK delivery bound (20–200 ms; 100 ms before any sample), rather than exhausting
all attempts at 20 ms intervals on a slower WAN. No new wire RTT claim is made.
The client also retries a keyframe when authenticated control is ready but no
initial picture/video arrives, without treating an unchanged healthy desktop
as a stalled stream.

When a peer explicitly reports zero completed pictures and two feedback windows
confirm congestion, startup can reduce the existing encoder budget to observed
delivery rate with repair headroom and request a fresh IDR. The same recovery
applies after pictures have started when progress stops for at least 750 ms,
two consecutive feedback windows show sustained source activity, and congestion
persists. An idle desktop does not meet these conditions. The existing 5 Mbps
quality floor (or a lower configured target) remains. Peers without the optional
progress report retain the existing controller behavior. FPS is not reduced.
This is a bounded recovery path, not a complete bandwidth estimator.

Loss feedback no longer counts every provisional NACK or retry as another lost
packet. It counts unique received repairs and fragments still absent at bounded
expiry/capacity eviction. Ordinary late original packets and duplicate repairs
do not inflate loss. This prevents reordering alone from unnecessarily driving
the encoder budget down. Delivered goodput likewise counts each accepted payload
fragment once, excluding duplicate repairs and fragment headers, rather than
mistaking repair traffic for useful bandwidth. Recovery still depends on usable bandwidth; this does
not guarantee video when a link remains below the configured quality floor.

The synthetic benchmark now fails when there is no video or an active-source
video gap reaches two seconds, even if control stays alive. Its optional
`--adaptive-source` sizes synthetic frames from the peer's budget; it does not
run a codec or represent a physical WAN benchmark.
The recorded eight-second simulation delivered about 60 FPS on emulated LAN
and 59 FPS on the lighter WAN. The congested case survived and recovered, but
its longest video gap was 2.24 seconds and **failed** the two-second video gate.
That case remains a limitation, not a passing performance claim. See the
[recorded results](../benchmarks/native-network-2.2.12.json).

## Scope and remaining validation

The user-side reports available during this work ended at 2.2.10; there was no
new physical 2.2.11 trace establishing every reported ten-second window exit.
The fixes above address reproduced defects, not every possible cause of a
black/frozen window. Screen capture permissions, GPU/driver behavior and the
original two-computer WAN cases require retesting. A real ~200 ms route is not
made into a 10 ms route by this release. Group audio remains unimplemented.
