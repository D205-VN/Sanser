# Audio output, speaker/microphone voice and elevated Windows input

Investigation: 2026-10-21, following physical-device reports on 2.2.18.
The three reported symptoms are investigated separately: ordinary Mac controlling
Windows becomes silent after a few seconds; group voice with speakers becomes
distorted; elevated Windows installer controls cannot be clicked.

## Observed evidence and its limits

Recent retained 2.2.18 legacy client reports on the Mac contain approximately
200 audio datagrams per second and increasing Opus decoded counts after startup.
The retained samples have zero codec errors, malformed packets, peer rejections
and replay rejections. A small transient authentication rejection count exists in
the report maxima; it is not evidence of persistent receive failure.

These counters show continued reception/decoding, not audible speaker output.
The previous diagnostic allowlist discarded the existing `played`/queue-drop
fields and had no device-completion counter. They cannot establish the exact
instant or cause of the physical-device silence.

## Legacy Mac output recovery

The previous player started an empty AudioQueue once during configuration. It
had no restart after a stopped queue, no watchdog for missing completion
callbacks, and called enqueue while holding the same mutex callbacks acquire.
Continued successful network decode therefore did not guarantee output progress.

The repair starts after enqueueing PCM, checks queue running state, restarts a
stopped queue, and recreates an output retaining buffers without completion for
250 ms. Enqueue/start errors also trigger bounded recovery. Recreating drops old
pending buffers rather than replaying them. The 20 ms device budget remains
bounded; Core Audio calls run outside the callback mutex. Old-queue callbacks
cannot replenish a replacement queue's budget.

Numeric diagnostics now distinguish submitted frames, device-completed frames,
queued frames, blocks containing a non-silent signal, starts, recoveries and
output errors. No PCM, encoded audio, device identity or voice content is stored.
Completion means the driver returned the buffer, not proof of audible sound.
Signed Core Audio error codes are allowed only for the dedicated error field.

The production player is exercised with fake Core Audio APIs and virtual time:
three seconds of successful output, stopped device, stalled callbacks, immediate
completion during enqueue, stale-buffer disposal and enqueue/start errors.
Disabling restart to simulate the former start-once behavior fails specifically
at the three-second stop; restoring recovery passes. No speaker is opened.

## Group voice timing and speaker echo

The voice worker previously consumed at most one 5 ms block per wake. A worker
waking every 7 ms because of processing overhead therefore supplied less than
48 kHz worth of PCM. The mixer now drains elapsed blocks, bounded to eight per
wake, rather than reducing the effective output rate. Its deterministic 7 ms
cadence regression delivers at least 395 blocks across two seconds without
dropping speech. This is independent of the network codec and device restart.

SpeexDSP 1.2.1 adds microphone-only acoustic echo cancellation before Opus
encoding. Its pinned source archive and bundled KissFFT have BSD notices in the
application and portable package. System music itself is not passed through the
speech processor. The reference combines actual app output and original local
system sound, with full Windows endpoint loopback taking precedence to prevent
double-counting. Capture uses first-sample device timestamps; output uses queue
start timing on Mac and WASAPI padding on Windows. See [voice design](../group-voice.md).

Synthetic multipath tests at 0/10/20/30/60/100 ms measured 26.8–34.3 dB echo
reduction, retaining near-end speech gain of 0.807–0.818 during simultaneous
playback and speech. Missing reference bypasses processing and mute/leave clears
adaptation. These are deterministic DSP results, not measured acoustic quality
on the user's speakers. Device clock drift, clipping, Bluetooth and imperfect
hardware timestamps remain physical-test cases.

## Installer-managed Windows administrator support

The old helper status checked that the service ran, but not whether its protected
host/helper copies matched the app update. Host selection could then fall back
to an ordinary host after a version mismatch. The new status compares bundled
and protected bytes and refuses this silent downgrade when support is enabled
but stale. Normal Windows install/update refreshes those protected copies through
an administrator-approved helper operation, retaining the original allowed user
even when the updater runs as SYSTEM. Explicit Disable survives updates.

Input detects a higher-integrity foreground installer and uses the existing
authenticated privileged broker, including after Secure Desktop returns to the
normal desktop. An unreadable target token is treated as unknown rather than
unelevated only by the protected host authorized for this broker.

The elevated Cancel regression exposed a separate handle-rights bug. Client
integrity was 8192 and target integrity 12288; the worker opened the desktop but
its input failed with Win32 5. The old generic `Unavailable` response then fell
back to ordinary SendInput, reporting three accepted events while neither moving
the pointer nor clicking Cancel. The worker now opens the interactive station
and desktop with the GUI input rights required by these operations. This changes
its handles, not desktop ACLs or UAC policy. Failure statuses distinguish console,
desktop and injection failure; rejected privileged injection no longer pretends
to succeed through the ordinary path. Numeric failures are rate limited in logs.

Windows CI on `160f2af` verified **direct=0, privileged=3, clicked=1**, without
skipping the actual click. The same job passed stale-copy detection, update as
SYSTEM retaining the original SID, explicit-disable preservation, stopped-service
removal, protected ACLs and unauthorized-caller rejection. The installer also
compiled in Windows CI. All 35 Windows native tests, including the older Mac-video
compatibility fixture discussed below, passed.

Normal uninstall removes a registered service even if it is
stopped or failed. The CI fixture uses a synthetic elevated Cancel window, a
medium-integrity protected host, stale-copy updates under SYSTEM, unauthorized
IPC denial and owner/ACL checks. An unavailable interactive CI desktop is an
explicit skip for the actual click; it is not reported as a successful click.
A same-integrity click baseline also checks whether a runner actually delivers
synthetic input before measuring cross-integrity behavior.
The NSIS installer is also compiled in Windows CI without publishing/installing
it. These fixtures do not prove a particular third-party installer works.

Local validation: all 29 native Mac tests, 248 frontend tests and 90 desktop
Rust library tests passed; formatting, lint and repository policy passed.
The final code CI run passed all nine jobs, including Windows compilation and
runtime fixtures, all 29 Mac native tests, desktop UI/Rust checks and NSIS
compilation: [CI 39632040632](https://github.com/D205-VN/Sanser/actions/runs/39632040632).
These fixes are source changes following 2.2.18; the already published 2.2.18
installer does not contain them.

## Decoder startup compatibility

Repeated Windows CI failures retained zero decoded pictures and requested new
keyframes while decoding the unchanged older Mac H.264 fixture. DecodeWorker
previously ended cold-start protection when a successful decode call emptied the
compressed queue. Media Foundation can accept input before producing any image;
this event did not prove output readiness.

Both production platform backends now report actual decoded-picture progress for
the current decoder generation. The existing bounded startup allowance ends only
after actual output and queue catch-up; normal/Ultra steady-state limits remain
unchanged. A deterministic regression accepts an IDR without output, blocks a
subsequent P-frame, verifies its reference chain survives, then signals output
and checks that the small steady-state limit returns. Simulating the old readiness
behavior fails that regression; restoring the new check passes. The unchanged
older, realtime and one-frame-at-a-time low-delay Mac fixtures all pass on
Windows in the final CI run, with the original output/progress assertions intact.

## Research anchors

- [Moonlight SDL output](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/audio/renderers/sdlaud.cpp): device buffer granularity, bounded queued duration and playback flow control belong to the output path; codec success alone is insufficient.
- [Mumble microphone processing](https://github.com/mumble-voip/mumble/blob/master/src/mumble/AudioInput.cpp): echo processing uses a separate playback reference before voice encoding. A codec or noise gate is not acoustic echo cancellation.
- [Microsoft SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput): input is subject to integrity isolation, and failure does not identify UIPI as its cause. Elevated input must use the authorized privileged path.
- [RustDesk native desktop selection](https://github.com/rustdesk/rustdesk/blob/master/src/platform/windows.cc): an architectural/API comparison of input desktop rights; no GPL implementation was copied into Sanser.
- [Microsoft SetProcessWindowStation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setprocesswindowstation): subsequent operations use the rights granted to the assigned station handle.

The user reports speakers with a built-in microphone and already enabled UAC
support. Physical speaker/mic feedback, device clocks and actual installer input
must be tested separately from synthetic processing and CI fixtures.
